Building on a component that is not deterministic

Seven ways this could be wrong, and the control for each

A language model is right most of the time, which is the hard case — a component that fails loudly is easy to engineer around. The unit of design is the control that recomputes the claim before anyone sees it. Ordered by what a mistake costs a patient.

Failure mode Control Why it exists
A finding names the wrong patient Refused unless the name is on the roster A name is a link to that person’s brief
A real finding never reaches the nurse Nine computed before the agents run The shortlist is twelve of a hundred
A stated number is wrong Every figure comes from a tool, not the model 120 open orders are 74 after triage
A finding is lost between agents Typed rows in a shared store, never prose About 27 cross between agents a run
The data layer stops answering Nine findings, or the run refuses to start An empty query looks like a quiet week
The brief contradicts the chart Reconciled against the clinician’s own note Three notes claim labs that never came back
A note tells the system what to do No tools, fixed schema; note text is data A planted order to report nothing came back quoted

Enforced twice: 64 tests re‑derive every tool’s answer in independent SQL — two seconds, no model — and nine invariants run across five live runs. A control nobody has watched fail is not a control, so each ships with a fault that trips it.

Each control has a deliberate fault in prototype/faults.py that makes it fire on demand

This is the slide that answers "how do you engineer with a component that is right most of the time". Lead on that sentence, because a component that fails loudly is the easy case and they will know it. The table is deliberately one line a cell: say the failure mode aloud and let the control sit there. The detail behind each row is in the demo, not on the slide, and these notes carry what to add if asked. Row 1 is first because it is the only one where being wrong is a patient-safety event rather than a quality problem. Row 2 is the important one intellectually - the eval did not just score the system, it changed the architecture, because it proved "the agent usually finds it" is a capability claim and not a safety property. Row 3 is the one to dwell on if they engage: a round alarming number that was wrong by a third and would have gone on a slide unchallenged. If asked whether the controls predated the errors: honestly, no, not all of them - the hazard list grew as I learned which judgements were load-bearing, which is how hazard analysis actually works, and the answer is in the commit history rather than reconstructed here. Row 7 is the one a health system will press hardest, and the order of the answer matters: schema and no tools FIRST, because that is the part that does not depend on the model behaving; the instruction second; the demonstration third. prototype/fixtures.py carries the attack and it takes about forty seconds to run live. What is NOT on this slide is on the next one, named rather than quietly absent.
