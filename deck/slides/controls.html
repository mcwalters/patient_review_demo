Building on a component that is not deterministic

Six ways this could be wrong, and the control for each

A language model is right most of the time, which is the hard case. The unit of design is the control that recomputes the claim before anyone sees it. Ordered by what a mistake costs a patient.

Failure mode Control
A finding names the wrong patient On the roster, and matching its own evidence
The nurse is told nothing when there is something Nine findings computed before the agents run — no nine, no run; and the report is checked back against them
A stated number is wrong Every figure comes from a tool, no opportunity for hallucination
A finding is lost between agents Typed rows in a shared store, never prose
The brief contradicts the chart Reconciled against the note — three claim labs that never resulted
A note tells the system what to do No tools, fixed schema — a planted instruction is reported, not obeyed

Enforced twice: 69 tests re‑derive every tool’s answer in independent SQL, and eight invariants run across five live runs. A control nobody has watched fail is not a control, so every runtime control ships with a fault that trips it.

Four of the six are runtime checks, and each has a planted fault in prototype/faults.py or fixtures.py; the other two are structural and cannot fail at runtime

This is the slide that answers "how do you engineer with a component that is right most of the time". Lead on that sentence, because a component that fails loudly is the easy case and they will know it. The table is two columns and one line a row: say the failure mode aloud and let the control sit there. Row 3 is where the 74-of-120 number belongs if they ask: it is the triage result, and it does not fit on the slide without reading as gibberish. Where a row carries an italic clause, that is a control which has already caught something real. Three rows have none: the wrong-patient check is precautionary and has never tripped, and the stated-number and lost-between-agents rows are structural - the model cannot compute a figure or pass prose because the architecture gives it no way to, so there is nothing to catch. Saying so is better than implying every row has a war story behind it. The detail behind each row is in the demo, not on the slide, and these notes carry what to add if asked. Row 1 is first because it is the only one where being wrong is a patient-safety event rather than a quality problem, and it is two checks rather than one. The roster stops an invented name. The second stops the worse error - a REAL patient's name on another patient's finding, which passes the roster cleanly and links straight to the wrong person's brief. Nothing can re-derive an arbitrary clinical claim, but the model writes the patient into its own evidence, so any name in the text that is not in the structured list is flagged deterministically. It reaches a finding only when the evidence names the patient, and how often that happens varies by run - every model finding on one cached run, 11 of 16 on the next, because the followup specialist wrote "a patient with diabetes" instead of a name. The floor's findings never need it; a join chose those patients. If asked how to close the gap: tell the extractor to name the patient in the evidence, a one-line prompt change - logged, not done, because it re-stales the demo caches. Row 2 is the important one intellectually and it carries two hazards that share a mechanism: the agent not finding something, and the database going quiet, which looks identical to a clean panel. The eval did not just score the system, it changed the architecture - a 22-month overdue INR surfaced in 1 run of 5, which proved "the agent usually finds it" is a capability claim and not a safety property. The nine are the answer to both: computed before anything runs, the run refuses to start without them, and the report is checked back against them. Row 3, the numbers, is the one to dwell on if they engage: a round alarming number that was wrong by a third and would have gone on a slide unchallenged. If asked whether the controls predated the errors: honestly, no, not all of them - the hazard list grew as I learned which judgements were load-bearing, which is how hazard analysis actually works, and the answer is in the commit history rather than reconstructed here. Row 7 is the one a health system will press hardest, and the order of the answer matters: schema and no tools FIRST, because that is the part that does not depend on the model behaving; the instruction second; the demonstration third. prototype/fixtures.py carries the attack and it takes about forty seconds to run live. What is NOT on this slide is on the next one, named rather than quietly absent.
