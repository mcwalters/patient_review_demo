Building on a component that is not deterministic

Six ways this could be wrong, and the control for each

A language model is right most of the time, which is the hard case — a component that fails loudly is easy to engineer around. So the unit of design is not the prompt, it is the control that recomputes the claim before anyone sees it. Ordered by what a mistake costs a patient.

Failure mode Control Why it exists
A finding names the wrong patient The store refuses any name not in the patient table and tells the agent which one it did not recognise. Panel‑level findings still need no patient. A name is a link that opens that person’s brief. 100 names are on the roster; a finding naming anyone else is refused, and the agent is told which one.
A real finding never reaches the nurse Nine findings are computed before the agents start, and the report is checked back against the store — anything high it failed to mention is raised above the narrative. The shortlist is twelve patients of a hundred, so something always comes off it. Agentic discovery is a capability, not a guarantee — the nine are guaranteed by construction.
A stated number is wrong No model computes what code can compute. Order triage, ACC/AHA staging, start‑date spread and drug‑to‑analyte lookup are tools; the model is handed the answer. Of 120 open orders, 74 are real once triage runs: 34 are superseded by a later result and 12 monitor a condition the patient does not have.
A finding is lost between agents Findings travel as typed rows in a shared store, never as prose. Every number a user sees is rendered from the row; the model cites [F..] ids. Around 27 findings cross between agents each run. Prose loses them in both directions; rows do not.
The data layer stops answering The floor’s size is known in advance, so it doubles as a tripwire: nine findings or the run refuses to start. A query that silently returns nothing is indistinguishable from a panel with nothing wrong. The failure would look like a quiet week.
The brief contradicts the chart Every pre‑visit brief is reconciled against the clinician’s own note before it renders — facts and care‑delivery claims both. Three encounters carry a note stating labs were ordered to guideline intervals where not one came back.

Each control is enforced twice: 57 tests re‑derive every tool’s answer in independent SQL in two seconds with no model, and eight invariants hold across five live runs. A control nobody has watched fail is not a control, so each one ships with a fault that trips it on demand.

Each control has a deliberate fault in prototype/faults.py that makes it fire on demand

This is the slide that answers "how do you engineer with a component that is right most of the time". Lead on that sentence, because a component that fails loudly is the easy case and they will know it. Work down the table; do not read every cell. Row 1 is first because it is the only one where being wrong is a patient-safety event rather than a quality problem. Row 2 is the important one intellectually - the eval did not just score the system, it changed the architecture, because it proved "the agent usually finds it" is a capability claim and not a safety property. Row 3 is the one to dwell on if they engage: a round alarming number that was wrong by a third and would have gone on a slide unchallenged. If asked whether the controls predated the errors: honestly, no, not all of them - the hazard list grew as I learned which judgements were load-bearing, which is how hazard analysis actually works, and the answer is in the commit history rather than reconstructed here. What is NOT on this slide is on the next one, named rather than quietly absent.
